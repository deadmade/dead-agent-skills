# Harness-independent Plugins Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Author shared plugins once and ship committed, native Claude Code and Codex terminal packages, including startup rules, notifications and Night City.

**Architecture:** A neutral catalog identifies shared resources and explicit native overlays. A deterministic build packages native manifests and plugin-owned hook declarations; ordinary packaged modules translate live events. Extend the existing distribution machinery, without an external framework or persistent service.

**Tech Stack:** Node 26+ standard library, erasable TypeScript for tools/installer/build logic, ESM JavaScript for packaged hooks, JSON definitions and native manifests, generated TextMate XML theme. No new runtime dependencies or Rust changes.

**Spec:** [spec.md](spec.md), approved 2026-10-31.

## Global Constraints

- Plugin identity/resources/dependencies: resolved in the shared catalog and native package emitters; never seen as native manifest formats by shared plugin handlers.
- Harness event inputs and responses: resolved in packaged harness entry adapters; never seen by shared notification policy, OS notification delivery or rule content.
- Capability availability: resolved in target validation and package generation; never assumed equivalent by shared plugin handlers.
- Native extensions: resolved in target resource selection; never loaded into another harness's package.
- Theme formats: resolved in theme adapters over the shared Night City palette; never encoded separately in shared color definitions.
- Host paths and configuration ownership: resolved in installation and packaged entry boundaries; never embedded as fixed user directories in shared handlers.
- Flow execution tools: resolved in existing host instruction adapters; never made a new tool-name requirement of shared flow policy.
- Preserve Claude marketplace IDs, plugin names, executable aliases, default release versioning and native config ownership.
- Respect CODEX_HOME and the existing Claude config path mechanisms. Preserve unrelated user configuration.
- Keep the installer free of runtime npm dependencies and follow its erasable TypeScript/module conventions.
- Do not edit vendored inputs or generated output by hand. Use transformations and package generation where adaptation is necessary; preserve upstream attribution.
- Preserve current uncommitted multi-harness work; establish an implementation baseline before attributing changes to this feature.
- Keep generated output deterministic and verify missing, changed and stale generated files. Linux/Windows differences must not produce persistent output drift.
- Test Windows and Linux command/path behavior, including spaces, native Node invocation and missing executables. Do not require Bash for shared runtime hooks.
- Do not add transcript parsing as a prerequisite for shared lifecycle behavior. Native transcripts are not assumed to be a stable cross-harness contract.
- Coordinate interface changes with the separate cockpit flow without implementing that app or a new capture format here.
- Commits/pushes are not part of this plan's authorization. Record the baseline HEAD, dirty patch and untracked inventory before execution; preserve them when creating a worktree or stay in the authorized working tree. Do not reset or commit the existing work.

## Before you write

Read the task and the code it touches. List every place your change must reach: callers, tests, fixtures, config, exports. Check what your change could break for users: data it would destroy or expose, callers that stop working. That is scope. Extra features are not.

## Review Focus

1. A generated hook launched from a directory containing spaces must reach its packaged module on Linux and Windows (Tasks 2 and 3).
2. A missing/changed/stale generated package must fail checks without removing authored or unrelated files (Tasks 3 and 7).
3. Existing managed AGENTS rules, untrusted hooks and edited user instructions must never result in premature removal or duplicate injection (Tasks 4 and 6).
4. A native plugin update must retain its stable ID, dependency closure, secrets handoff and optional resource paths (Tasks 1, 3 and 7).
5. Malformed/unknown native input and unsupported optional events must not become false completion notifications or successful control decisions (Tasks 1 and 2).

## File structure and ownership

- `catalog/plugins.json`: authored neutral metadata/source/resource/target catalog. This avoids adding files under wholly vendored plugins. Shared hooks remain plugin-owned at `plugins/default/hooks/shared.json`.
- `tools/installer/core/catalog.ts`: pure catalog types and target selection/validation; no filesystem I/O.
- `tools/installer/system/catalog.ts`: reads the neutral catalog relative to a supplied checkout/installed-package root. Runtime selection needs this shipped JSON, never authored plugin folders or hook source files.
- `tools/installer/system/packages.ts`: deterministic package construction and native marketplace output; delegates native shapes to `tools/installer/core/package-adapters.ts`.
- `tools/installer/system/portable.ts`: remove after migrating internal callers in Task 3; keep only public build:codex/check:codex command aliases. Move portableText into the Codex packaging adapter. No permanent parallel build API.
- `plugins/default/hooks/runtime/`: packaged input/output adapters and runner; shared feature code stays adjacent in the plugin.
- `portable/plugins/<name>/`: preserve existing Codex distribution paths. Add `portable/claude-code/plugins/<name>/` for generated Claude packages and a nested Claude marketplace. Root marketplaces reference the matching generated roots.
- Existing source `.claude-plugin/plugin.json` files become explicit Claude overlays and development/test manifests. Shared identity/description/version come from the neutral catalog/root version; overlay-only dependencies/userConfig/LSP/mod settings remain native. Reject conflicting shared identity rather than hiding it.
- Generated subtree lists below are file allowances for deterministic output, never permission for manual edits. All other file changes require the flow's deviation process.
