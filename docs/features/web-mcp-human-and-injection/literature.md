## Where the evidence agrees

- Header/browser consistency and interaction timing matter; fingerprint patching adds inconsistencies and performed worse (E1, E3, E5, E6).
- A real, headed, local browser is the best-placed configuration (E1 for headed, E4 for local; E4 used university IPs, not residential).
- No injection defence survives an adaptive attacker (E13, E14). The rows near 0% constrain what an injected instruction can do (destination allow-list, privilege separation, CaMeL) rather than detect it (E15, E16, E22).

## Conflicts and caveats

- E3 says behavioural signals expose agents; E4 says local agents passed nearly every defence. [inferred] E3's classifier is the authors' own and deployed vendors may not run one like it; E4's reCAPTCHA v3 and Turnstile may score behaviour, so this tension is unresolved. Whether E3's "Claude" agent is the same product as E4's Claude Chrome isn't established.
- Static ASRs (E12, E15, E17) vs adaptive ones (E13, E14) differ by tens of points; read static numbers as upper bounds on benefit.

## What is not covered

- Request spacing, burst limits and per-engine thresholds (E8, E10).
- Humanised mouse and keystroke generators: they appear only as related-work citations inside E3 and were not opened.
- Measured ASR for localhost/private-address blocking, disabling JS eval, or CSS-hidden-text/comment stripping on tool output. E16 is the nearest (destinations).
- Whether Google, Bing, DuckDuckGo or Brave use E3's signals on search pages.
- Stealth stacks as policy: the evidence here is only that they performed worse (E5); no legal or terms-of-service assessment.
